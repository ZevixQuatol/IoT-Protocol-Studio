# IoT Protocol Studio 开发环境与构建

## 当前阶段

第一阶段只交付 Windows x86_64，采用以下结构：

```text
React + TypeScript Web UI
        ↓ WebView Bridge
Windows Host
        ↓ C++ API
Portable C++ Core
```

当前已有五条可运行纵向切片：Windows 客户端可以调用 C++ Core 完成 HEX 规范化、ASCII 预览、SUM8、XOR8 和 CRC16/MODBUS；CLI 可以加载并校验 Protocol Schema v0.1 YAML；Core 可以根据 Schema 对固定布局 bool、整数、浮点、UTF-8 string、bytes、最小 Length Field 和固定 Primitive Array 进行双向 Encode/Decode；协议级入口可以根据 `ProtocolSchema + Message 名称` 对 HEX/Binary 完成 Decode/Encode；Workspace Core 和 CLI 可以从普通目录加载 `project.yaml` 并校验项目引用的 Protocol Schema，Workspace Core 还可以创建嵌套 Protocol Schema 并安全写回项目引用。

这不表示完整 Schema Decode/Encode、真实 Transport 或完整 Simulator 等 MVP 功能已经完成。

## 目录

```text
IoT Protocol Studio
├── core/
│   ├── include/iotps/core/{schema,workspace,codec,transport,simulator,testing}/
│   ├── src/{schema,workspace,codec,transport,simulator,testing}/
│   └── CMakeLists.txt
├── apps/
│   ├── cli/
│   ├── desktop-win/
│   └── web-ui/
├── test/
│   ├── unit/
│   ├── integration/
│   ├── vectors/
│   └── fuzz/
└── docs/
```

Core 不依赖 Win32、WebView、React 或 JSON。Windows Host 负责 WebView 生命周期、Bridge 和平台信息，Web UI 只调用稳定的命令接口。

Core 已拆分为独立 CMake 模块目标：

```text
iotps::common
├── iotps::schema
│   └── iotps::workspace
├── iotps::transport
└── iotps::codec ──→ iotps::schema
                     ├──→ iotps::simulator ←── iotps::transport
                     └──→ iotps::testing

iotps::core = 供现有应用使用的聚合 Facade
```

Workspace 复用 Schema 加载项目协议文件，只暴露标准文件系统类型。Transport API 只收发 ByteBuffer，不依赖 Schema 或 Codec。Simulator 组合 Codec 与 Transport；Testing 当前提供 Test Case、Assertion 和 Report 基础。详细边界见 [Core 模块架构](<./Core 模块架构.md>)。

## 依赖

- Windows 10/11 x86_64
- Visual Studio BuildTools 2022 或更新版本
- Windows 10/11 SDK
- CMake 3.24 或更新版本
- Node.js 20 或更新版本
- npm
- WebView2 Runtime
- clang-format（用于 C/C++ `format` 和 `format-check`）

CMake 配置阶段会按固定版本下载：

- `webview/webview` 0.12.0
- `Microsoft.Web.WebView2` SDK（由 `webview/webview` 获取）
- Rapid YAML 0.16.0（固定归档 URL 和 SHA-256，仅作为 Schema、Workspace 私有实现依赖）

这些依赖不会配置项目 Git remote。

## 安装 Web UI 依赖

```powershell
cd apps/web-ui
npm install
```

项目提交 `package-lock.json`。新环境初始化时可以使用 `npm ci` 保持前端依赖可复现；CMake 只执行 `npm run build`，不会在每次 C++ 增量构建时重装依赖，因此可以与 Vite 开发服务器同时运行。

Web UI 开发依赖中固定包含 Prettier，版本记录在 `package.json` 和 `package-lock.json`。

## 代码格式化

仓库根目录提供：

- `.editorconfig`：统一 UTF-8、LF、文件末尾换行、空格缩进和尾随空格规则。
- `.clang-format`：格式化 `core/`、`apps/` 和 `test/` 中的 C/C++ 文件。
- `.prettierrc.json`：格式化 React、TypeScript、CSS、HTML 和 Web UI JSON 配置。
- `.prettierignore`：排除构建产物和依赖目录。

检查格式，不修改文件：

```powershell
cmake --build --preset windows-x86_64-debug --target format-check
```

自动格式化：

```powershell
cmake --build --preset windows-x86_64-debug --target format
```

也可以只检查或格式化 Web UI：

```powershell
cd apps/web-ui
npm run format:check
npm run format
```

`format` 和 `format-check` 是开发工具目标，不参与普通应用构建。新环境如果缺少 clang-format 或 npm，显式运行对应目标会失败并显示缺失工具，不会在 CMake configure 阶段阻止普通构建。

- HEX 解析单元测试

- Schema 领域模型与校验单元测试
- Protocol Schema YAML/文件加载、诊断位置和合法/非法向量单元测试
- Project Workspace YAML、跨平台相对路径、协议加载、嵌套 Protocol 创建/回滚和稳定诊断单元测试
- 固定长度 Primitive/string/bytes/Array Encode/Decode、大小端、固定 `length`/`offset`、padding、数值/长度/数量范围和错误诊断单元测试
- Schema YAML → 非连续 HEX → Primitive Decode → expected golden vector 集成测试
- Schema YAML → Decode → 固定布局 Primitive Encode → golden HEX → Decode round-trip 集成测试
- Schema YAML → UTF-8 string/bytes Decode → expected → Encode round-trip 集成测试

- Schema YAML → 固定 Array Decode/Encode → 元素范围 → Length 自动回填 → golden round-trip 集成测试
- Protocol Schema + Message 名称 + HEX/Binary → Decode/Encode → golden round-trip 和错误映射集成测试

- 测试向量驱动的 Engine 集成测试

- 可选 libFuzzer 入口

## CLI

```powershell
iotps version
iotps inspect "AA 55 01 0A 78 56 34 12 03 02 01 A8 C3"
iotps schema validate .\docs\examples\SmartSensor.protocol.yaml
iotps project validate .\test\vectors\project\smart-sensor
```

`schema validate` 和 `project validate` 成功返回 `0`，文件、Schema 或 Project 错误返回 `1`，命令用法错误返回 `2`。格式定义、诊断字段和兼容规则见 [Protocol Schema v0.1](<./Protocol Schema v0.1.md>) 和 [Project Workspace v0.1](<./Project Workspace v0.1.md>)。

## Web UI 独立开发

```powershell
cd apps/web-ui
npm run dev
```

浏览器预览使用 TypeScript 实现的预览适配器。Windows Host 中运行时使用 C++ Core。

发布版 Host 不使用 `file://` 直接打开 Vite 产物。WebView2 会拦截 `file://` 页面加载本地 ES Module，表现为窗口存在但内容为空。Host 将可执行文件旁的 `web-ui` 目录映射为受限的 `https://iotps.local/` 虚拟主机，再从该同源地址加载页面；不需要开启全局的 `--allow-file-access-from-files` 权限。

Web UI 提供中文和英文两套完整界面。首次打开时根据浏览器或操作系统语言选择中文（`zh-*`）或英文，之后可以通过标题栏右侧的语言控件手动切换。用户选择保存在浏览器存储的 `iotps.locale` 键中，桌面 Host 和浏览器预览分别在各自的 WebView/浏览器配置中保存。

Core 和 Host 返回稳定的错误码与结构化数据，不返回面向用户的本地化文案。Web UI 根据错误码完成翻译，避免语言逻辑进入跨平台 C++ Core。

Core 中返回单个成功值或错误的 API 统一使用 `Result<Value, ErrorType>`；无返回值操作使用 `Status<ErrorType>`。模块错误统一使用 `Error<ModuleErrorCode>`，包含稳定错误码、领域路径、可选偏移和非本地化技术细节。Schema 批量校验继续返回诊断集合，但集合元素使用同一 Error 结构。

如果希望 Windows Host 加载 Vite 开发服务器，可以先设置：

```powershell
$env:IOTPS_WEB_UI_URL = 'http://127.0.0.1:5173'
```

随后启动 `IoT Protocol Studio.exe`。未设置该变量时，Host 加载可执行文件旁的静态 Web UI。

## 平台边界

第一阶段不创建 `core-AMD64` 或 `core-ARM64`。Core 保持单一源码树，平台和架构由 CMake Preset、编译器和产物目录决定。

Windows 专属实现只允许进入 `apps/desktop-win` 或后续明确的平台适配目录；Core 公共头文件不得包含 `windows.h`、WebView2 或 GUI 类型。
